# Критерии оценки нового кода (devai)

Версия 1.0 · 2026-11-01
Применимо к: изменениям в workspace `devai-core` / `devai-store` / `devai-cli`, вносимым агентом-разработчиком.

---

## 1. Модель оценки

```
S = GATE × Σ (w_i × s_i),  s_i ∈ [0, 1]
```

- **GATE** ∈ {0, 1} — все шлюзы (раздел 2) пройдены. Любой непройденный шлюз → S = 0, дальнейшее оценивание бессмысленно.
- **w_i** — веса критериев (раздел 3), Σ w_i = 1.
- **s_i** — балл критерия по якорной шкале (раздел 4).

Принцип распределения весов: **~60 % веса — детерминируемые проверки** (команды, grep, тесты), **~40 % — суждение по рубрике**
(код-ревью). Суждение не должно доминировать, чтобы оценка была воспроизводимой; механика не должна доминировать
過度но, потому что «зелёный build с плохой архитектурой» — это техдолг, а не результат.

### Пороги вердикта

| S       | Вердикт                                  |
|---------|------------------------------------------|
| ≥ 0.85  | Принять (merge)                          |
| 0.60–0.84 | Рework: список нарушений по критериям  |
| < 0.60  | Отклонить                                |
| GATE=0  | Отклонить без обсуждения весов           |

## 2. Шлюзы (gates) — бинарные, без веса

| #   | Шлюз | Проверка | Почему gate, а не критерий |
|-----|------|----------|---------------------------|
| G1  | Workspace собирается | `cargo build --workspace` exit 0 | нерабочий код нельзя оценить иначе |
| G2  | Тесты зелёные | `cargo test --workspace` exit 0 | падающий тест = известная поломка, а не «−балл» |
| G3  | Local-first нарушен нет | ни одной сетевой crate/вызовa: `grep -RInE "reqwest|hyper|ureq|attohttpc|TcpStream|UdpSocket" crates/` пусто; новых сетевых зависимостей в Cargo.toml нет | суверенность данных — продуктовая константа, не оптимизируемая traded-off |
| G4  | Нет секретов в репозитории | `grep -RInE "(api[_-]?key|password|token|BEGIN (RSA\|PRIVATE))" crates/` без real-hits; в diff нет `.env`, ключей | утечка необратима |

Доп. **мягкие флаги** (не обнуляют, но помечают diff красным для ревьюера):
新增 panic-path: `unwrap()/expect()` вне `tests/`, `mod test*` (см. C4).

## 3. Критерии и веса

| #  | Критерий | Вес | Способ измерения |
|----|----------|-----|-----------------|
| C1 | **Функциональная корректность** — поведение соответствует постановке: переходы state-машины, запреты (sovereignty rules), optimistic concurrency (`lock_version`), идемпотентность событий | **0.25** | приёмочные тесты + существующие `crates/*/tests/`; доп. пробы «запрещённый переход из каждого состояния» |
| C2 | **Архитектура и границы слоёв** — `core` остаётся чистым (без IO-зависимостей), IO только в `store`, `cli` тонкий; направление зависимостей не нарушено | **0.15** | grep Cargo.toml core (там не должно быть rusqlite/fs/network); ревью: нет ли `std::fs`/`Connection` в core; нет ли бизнес-правил в cli |
| C3 | **Качество тестов нового кода** — новые ветки/переходы покрыты; есть negative-кейсы (не только happy path); тесты проверяют поведение, а не привязку к реализации | **0.10** | coverage `cargo llvm-cov` (ориентир ≥80 % diff-coverage); ручной просмотр: покрыты ли InvalidTransition, терминальные/hold-состояния, stale-артефакты |
| C4 | **Надёжность и обработка ошибок** — типизированные ошибки (`thiserror`), сообщения с контекстом/подсказкой (паттерн `CoreError::hint`), отсутствие паник в library-путях, корректные exit-коды CLI | **0.10** | `grep -RIn "unwrap()\|expect(" crates/*/src/` = 0 (или обоснованные комментарий-protected инварианты); CLI: ошибка → exit ≠ 0 и человекочитаемое сообщение |
| C5 | **Качество стиля и линтер** — `cargo clippy --workspace --all-targets -- -D warnings` чисто; `cargo fmt --check` чисто; читаемые имена, функции разумного размера, нет дублирования логики переходов | **0.10** | команды, exit 0/1 → s=1/0; частичный балл за fmt при чистом clippy и наоборот |
| C6 | **CLI-контракт и UX** — `--help`/подкоманды описаны; машинно-читаемый вывод (`--json`) стабилен и сериализуется; обратно совместим с предыдущими вызовами (не сломаны существующие флаги/поля); идемпотентность команд повторного вызова | **0.10** | прогон всех подкоманд с/без `--json`, `jq`-парсинг вывода; дифф help-текста; сценарий «повторить команду дважды» без побочных дублей |
| C7 | **Соответствие доменной модели** — история неизменяема (артефакты помечаются STALE/SUPERSEDED, не удаляются), события append-only, категории данных не смешиваются, схема миграций store согласована с типами core | **0.10** | ревью diff на DELETE из tables событий/артефактов; тест на повторный переход; сверка rows.rs ↔ types.rs |
| C8 | **Документация** — rustdoc на публичных API crate, обновлён README/docs при изменении контракта, commit-message/changes описывают зачем | **0.05** | `cargo doc` без warning'ов на новых pub-элементах; наличие докстрингов ≥90 % новых pub items |
| C9 | **Производительность/ресурсы (соразмерно задаче)** — нет N+1 запросов в store, нет квадратичных обходов на горячих путях, транзакции там где группа записи атомарна | **0.05** | ревью SQL-паттернов; при наличии bench — время не хуже baseline ×1.5 |

Σ w = 1.00

### Почему такие веса

- **C1 (0.25)** — единственный критерий, ошибка в котором ломает пользователя сразу; всё остальное — скорость деградации.
- **C2 (0.15)** — devai спроектирован слоями; протекающая в core IO-зависимость окупает любые будущие фиче-тесты ценой переделки.
- **C3–C7 (по 0.10)** — равный средний эшелон: каждый сам по себе не катастрофа, но их сумма (0.50) — это то, что отделяет «работает» от «можно поддерживать».
- **C8–C9 (по 0.05)** — полезно, но не должно давать агенту набрать баллы косметикой, когда C1–C2 просели.

## 4. Якорная шкала s_i (для критериальных оценок суждением)

| s | Уровень |
|---|---------|
| 1.0 | Все проверки пройдены, нарушений нет |
| 0.7 | Есть замечания, не влияющие на корректность (2–3 мелких) |
| 0.4 | Есть существенное нарушение, но оно локально и не блокирует merge-поток (rework по списку) |
| 0.1 | Нарушение затрагивает инвариант (например паника в library-пути, изменение истории событий) |
| 0.0 | Критерий не выполнен / требование постановки проигнорировано |

Для чисто бинарных проверок (C5, шлюзы): 1/0 без градации.

---

## 5. Порядок применения

1. Прогнать G1–G4.任一 fail → вердикт «отклонить», отчёт = список непройденных шлюзов.
2. Прогнать автоматические проверки C1–C8 (команды из таблицы «Способ измерения»); сохранить raw-output рядом с отчётом — оценка должна быть аудируемой.
3. Код-ревью по рубрике для C2/C3/C6/C7/C9 (и разрешение tie-break'ов автоматических частей).
4. Посчитать S, выдать вердикт + покритерийный breakdown:
   `{gate, per_criterion: [{id, w, s, evidence}], score, verdict}` — в machine-readable виде (json) для последующей автоматизации.

### Замечания по анти-геймингу

- Приёмочные тесты C1 держит оценщик, не разработчик (агент не пишет критерии, по которым его оценивают).
- C3 считает coverage **по diff**, а не по проекту — иначе балл накручивается тривиальными тестами старого кода.
- C4 grep-база фиксируется до начала работы агента (baseline unwrap'ов измеряется относительно неё, новые — штраф).
