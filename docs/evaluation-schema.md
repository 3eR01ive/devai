# Декларативная схема профилей оценки

Версия 0.2 · 2026-11-01 (scoring и формат вердикта стабилизированы первым прогоном по реальному коду)
Файлы-профили: `docs/profiles/*.yaml`. Пример наполнения — `docs/profiles/devai.yaml`.
`evaluation-criteria.md` остаётся частным случаем наполнения этой схемы; веса вынесены из замороженного статуса в профиль (см. §2.5).

---

## 1. Мотивация

Оценка не жёстко зашита в инструмент, а описывается профилем. Требования, которые схема обязана покрыть:

1. **Тип ошибки → множество критериев.** Нарушение одного типа (например `architecture/magic`) может детектироваться несколькими проверками, и одна проверка может детектировать несколько типов. Связь — many-to-many, декларированная с обеих сторон.
2. **Гибкость типов оценок.** Архитектурная, надёжность, UX, доменная инвариантность — всё это `evaluation`-группы, добавляемые без изменения инструмента: новая оценка = новый блок в профиле.
3. **Кастомизация.** Профили наследуются (`inherits`), переопределяются по `id`, добавляются project-specific проверки.
4. **Воспроизводимость.** Каждая проверка либо механическая (probe — команда/скрипт), либо рубрикальная (анкерная шкала + обязательный evidence), либо гибрид.
5. **Скоринг — часть схемы, но опционален для валидности.** Профиль без `scoring` валиден (только вердикт-составляющая не вычислима); формат `scoring` стабилизирован в §2.5 после первого прогона.

## 2. Грамматика (уровни)

```
profile
├── version, project            — identity
├── inherits: [profile-id…]     — merge base'ов; позже объявленный конфликтует-по-id выигрывает
├── error_types: map            — ТАКСОНОМИЯ ошибок (атом нарушения)
├── gates: [gate…]              — бинарные шлюзы (не скорингуются)
├── evaluations: [evaluation…]  — группы оценок (типы оценок)
│   └── checks: [check…]        — критерии внутри группы
└── scoring: {…}                — опционально; формат: §2.5 (verdict-функция, §2.6 — обязательный отчёт)
```

### 2.1 error_type (атом таксономии)

```yaml
error_types:
  architecture/magic:
    desc: >            # человекочитаемое определение, обязательно
      Немотивированное числовое/строковое значение в коде, не выраженное
      именованной константой с объяснением, откуда оно взялось.
    severity: minor    # catastrophic | major | minor | cosmetic
    default_fix_hint: вынести в const с комментарием-обоснованием
```

- `id` — именованное пространство `category/name`; категория = каталог типов оценок, но **привязки к evaluation у error_type нет** — только check объявляет, что он детектирует (см. ниже). Это позволяет один тип ошибки обслуживать нескольким оценкам.
- `severity` — влияющий на scoring позже; в схеме это просто метка.
- Таксономия открытая: категории не фиксированы (`architecture`, `reliability`, `correctness`, `ux`, `process`, …).

### 2.2 gate

```yaml
gates:
  - id: build-green
    desc: workspace компилируется
    probe: { cmd: "cargo build --workspace" }   # exit 0 == pass
```

Gate = бинарный check без severity: не пройден → профиль возвращает `verdict: rejected-gate` до оценивания проверок.

### 2.3 evaluation (тип оценки)

```yaml
evaluations:
  - id: architecture
    title: Архитектурная оценка
    desc: границы слоёв, идиомы, принципы, магия
    checks: [ … ]
    # опционально:
    applies_to:                       # фильтр, когда оценка вообще включается
      paths: ["crates/**"]            # glob-и против diff-путей задачи
      when: "diff touches > 1 crate"  # предикат над задачей (язык предикатов — отдельное решение)
```

`evaluation` — это **не** таксономический слой для ошибок; это упаковка проверок и процедура их исполнения. Между evaluation и error_types связь только через `check.detects`.

### 2.4 check (критерий) — центральный элемент

```yaml
checks:
  - id: arch/idiom-consistency
    statement: >            # инвариант: ЧТО должно быть верно, одной фразой
      Код внутри crate использует идиомы, принятые для его роли:
      core — чистые функции-трансформеры, возвращающие Mutation;
      store — только данные и SQL; cli — только разбор и вывод.
    detects: [architecture/idiom-misuse, architecture/idiom-inapplicable]
    verify: rubric          # mechanical | rubric | hybrid
    # mechanical/hybrid:
    probe:
      - { cmd: "crates/*/tools/lint_layers.sh", map: "stdout JSON → violations[]" }
    # rubric/hybrid:
    anchors:                # якорная шкала обязательна для rubric-проверок
      "1.0": нарушений нет
      "0.7": 2–3 косметических отклонения, инвариант цел
      "0.4": существенное отклонение, локально исправимо
      "0.1": нарушен инвариант слоя (IO в core и т.п.)
      "0.0": требование проигнорировано
    evidence: required      # rubric-оценка обязана приложить цитаты кода
    reviewer: human         # human | agent | either — кто имеет право выставлять балл
```

Поля `check`:

| поле | обязательно | назначение |
|------|-------------|-----------|
| `id` | ✓ | namespaced уникальный ключ (переопределение по нему при `inherits`) |
| `statement` | ✓ | инвариант одним-двумя предложениями; evaluator-человек понимает суть не читая probe |
| `detects` | ✓ | ≥1 error_type. Обратное направление: `profile.error_types` не знает о checks — соответствие вычисляется при загрузке (индекс type→checks) |
| `verify` | ✓ | mechanical: probe решает всё; rubric: anchors+evidence решают; hybrid: probe даёт кандидатов-нарушений, rubric их подтверждает/отклоняет (снижает false-positive от grep-подобных probe) |
| `probe` | для mechanical/hybrid | {cmd} \| {script} \| {tool}: структурированный вызов, вывод парсится в violations[]; violations не классифицированы → не относятся к profile |
| `anchors` | для rubric/hybrid | map score→описание; ключи — строковые числа; мин 3 градации; 1.0 и 0.0 обязательны |
| `evidence` | ✓ (default `required` для rubric) | required \| optional \| none |
| `reviewer` | (default either) | важно для анти-гейминга: часть checks может быть human-only |
| `suppression` | опционально | как допускать исключения: `allow_comment: "// eval-ignore: <id> — reason"`, и обязывать tool учитывать их |

### 2.5 scoring

```yaml
scoring:
  aggregation: per-check      # per-check | per-type | worst-anchor (§3.5)
  theta: 0.80                 # порог PASS по итоговому S
  floors:                     # красные линии: min s_i по max severity в check.detects
    catastrophic: 0.7         #   (вычисляется при загрузке, отдельной таблицы нет)
    major: 0.4
    minor: null
  blocked_policy:
    max_blocked_weight: 0.20  # суммарный вес невыполненных checks
    over_cap: INCONCLUSIVE    # ренормировка запрещена, вердикт не выдаётся
    under_cap: renormalize    # пересчёт по выполненным + gaps[] в отчёте
  weights:
    <check-id>: 0.nn          # Σ по всем активированным checks = 1.0; 0.0 = meta-проверка
```

Вердикт-функция (детерминирована, ничего не «решает на глаз»):
```
PASS         : gate=1 ∧ floors met ∧ S>=theta ∧ нет pending_human
FAIL         : gate=0 ∨ любой пол нарушен ∨ S<theta
INCONCLUSIVE : blocked_weight>cap ∨ reviewer:human не подписал
S            : Σ w_i·s_i, делённый на Σ w_i выполненных checks (gates не скорингуются)
```
Некомпенсируемость обеспечивают полы, а не суровость весов: плохая дорогая проверка не «съедается» красивыми мелкими.

### 2.6 Формат отчёта (what QA emits)

Референс-исполнение: `docs/qa-run.py` (stdlib-only, читает профиль + run.json
оценщика; порядок «ЧТО ПЛОХО» = worst-first по severity худшего detectable типа
проверки; нарушение формата = невалидный отчёт).

Число — шапка; дальше только претензии, по убыванию вреда. Каждая строка:
**что + где (file:line) + чем кончится**. Без «улучшить читаемость». Без похвалы.
Блок «НЕ ПРОВЕРЕНО» обязателен, если есть blocked — он не сваливается в PASS.
`pending_human` отображается отдельной строкой: чья подпись нужна и по какой проверке.

Шаблон:
```
ВЕРДИКТ: <ПРОШЁЛ|НЕ ПРОШЁЛ|ВЕРДИКТ НЕ ГОТОВ> (<S>/1.00, порог <theta>, красных линий <нет|список>)
ЧТО ПЛОХО:
1. …
НЕ ПРОВЕРЕНО: …
ЖДЁТ ЧЕЛОВЕКА: …
```

## 3. Как ошибка становится оценкой (семантика many-to-many)

Классический прогон (audit-run):

1. Gates → иначе stop.
2. Для каждой `evaluation` (отфильтрованной `applies_to`) исполнить checks:
   - mechanical → violations[] из probe;
   - rubric/hybrid → наблюдатель/агент выставляет anchor-score + evidence.
3. Каждая **подтверждённая** violation классифицируется в один из `error_types` из `check.detects` (probe может эмитировать `type` напрямую).
4. Теперь оба индекса живые:
   - `check → violations` — для анкера этого check;
   - **`error_type → {checks, violations}`** — «множество критериев на каждый тип ошибки»: если violations типа `architecture/magic` найдены и через grep-probe, и через ревью-рубрику, это одно и то же нарушение, учтённое один раз (дедуп по (file, line, type)); но **разные** нарушения одного типа, пойманные разными критериями, не схлопываются.
5. Агрегация (модель на выбор профиля, когда придёт scoring):
   - **per-check** — классика: score_i по якорям, потом Σ w_i·s_i;
   - **per-error-type** — штраф за каждый тип `error_types` имеет `impact`, score = 1 − Σimpact/Σmax (тип учитывается один раз независимо от числа критериев, его нашедших);
   - **worst-anchor** — за группу берётся худший check (жёстко для correctness-оценок, где один InvalidTransition перечёркивает всё остальное).
   - смещение схемы к per-type модели — причина держать severity на error_type, а не на check.

## 4. Слияние профилей (inherits)

- Последовательность base'ов применяется слева направо; `profile` поверх.
- Сопоставление по `id`: present в двух → shallow-merge полей; поле `null` — не «удалить», а «сбросить к base»; удаление — отдельная операция: `{ id: x, disabled: true }`.
- `detects` — union при merge (проверка, расширенная в child-профиле, детектирует больше типов).
- Конфликт `anchors` при merge — запрет (валидатор требует child переопределить anchors целиком).

## 5. Валидация профиля (что принимает tool)

Инварианты, проверяемые при загрузке — до любого исполнения:

V1. Все `detects` ссылаются на объявленные `error_types` (обратное — не обязательно: тип может не иметь ни одного check'а = «зарезервирован таксономией, критериев пока нет»).
V2. Уникальность `id` в пределах profile (после merge).
V3. mechanical/hybrid имеют хотя бы один probe; probe.cmd выполняется в корень workspace (описательная проверка: `sh -c 'which …'` не валидируется статически).
V4. rubric/hybrid имеют anchors ≥3 градаций, включая 1.0 и 0.0.
V5. `error_types.*.severity` ∈ {catastrophic, major, minor, cosmetic}.
V6. gate'ы не содержат anchors (только pass/fail).
V7. при `scoring.weights` объявлено — Σ весов = 1.0 (0.0 допустим для meta-проверок, например `proc/evidence-completeness`), и множество weighted checks = множество активированных checks без пропусков; `aggregation: worst` — веса запрещены. (Поймано первым прогоном: забытый вес проверки — именно этот инвариант его требует.)
V8. полы не объявляются в профиле вручную: они выводятся из max severity в `check.detects`; попытка завести отдельную таблицы floor'ов — валидатор отвергает (единственный источник — error_types.severity).

## 6. Открытые вопросы (не блокируют grammar v0.1)

- Язык предикатов `applies_to.when` — mini-DSL? или пока только `paths`.
- Формат violations[] из probe (stdout JSON? отдельный файл?) — стандартизировать в v0.2.
- Кто эмитит `type` при hybrid: probe-хэд должен быть детерминированным; иначе классификация плывёт.
- `reviewer: agent` требует lock'а на промпт-шаблон рубрикации — иначе оценки невоспроизводимы между запусками.
